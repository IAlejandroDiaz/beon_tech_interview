# Design — Fun Facts

## Overview

Fun Facts adds a read-only endpoint, `GET /fun-fact`, to the existing RAG
service. It returns a short, playful, context-grounded fact about BEON.tech,
generated by the local LLM and grounded strictly in the knowledge-base
snippets. It reuses the existing RAG building blocks (`knowledge_base`,
`vector_store`, `llm`) and adds only a small, focused prompt builder and a route
handler.

The design keeps the two retrieval modes of the feature explicit:

- **Topic-focused** (`?topic=<text>`): embed the topic, retrieve the most
  relevant snippet(s) via the vector store — the RAG path.
- **Random** (no topic): pick a snippet at random from the knowledge base — no
  embedding needed, cheap, and keeps repeated calls feeling fresh.

Both modes feed the same grounded prompt and LLM call, then return the same
structured JSON shape, mirroring `/ask` for consistency.

## Architecture

```
GET /fun-fact?topic=...
        │
        ▼
  ┌──────────────────────────────────────────────┐
  │  fun_fact handler (main.py)                    │
  │                                                │
  │  topic present? ──yes──► VectorStore.retrieve  │  (embed + cosine search)
  │        │                                       │
  │        no                                      │
  │        └──────────► VectorStore.sample         │  (random snippet)
  │                                                │
  │  build_fun_fact_messages(snippets)  ──────────►│  (prompt.py)
  │  LLMClient.complete(messages)       ──────────►│  (llm.py → vLLM)
  │                                                │
  │  assemble FunFactResponse                      │
  └──────────────────────────────────────────────┘
        │
        ▼
  { fact, sources, topic, model, timestamp }
```

No new external dependencies. No new storage. The only new code is a prompt
builder, two small additions to `VectorStore`, and the route + response model.

## Components and Interfaces

### 1. VectorStore additions (`vector_store.py`)

The store currently exposes only `retrieve`. The random mode and the empty-KB
guard need two small, well-scoped additions:

```python
def sample(self, k: int = 1) -> list[dict]:
    """Return k randomly selected snippets (no embedding/query).

    Shape matches `retrieve`: [{ "text": str, "score": float }]. Because no
    similarity is computed, `score` is reported as None to signal "not ranked".
    """

@property
def size(self) -> int:
    """Number of indexed snippets. Used to guard the empty-KB case."""
```

- `sample` uses `random.sample` over the in-memory `self._snippets`, capped at
  the corpus size. It returns the same dict shape as `retrieve` so the handler
  treats both paths uniformly; `score` is `None` because random selection is
  not a similarity ranking (honest signal, not a fake score).
- `size` lets the handler short-circuit with a clear error when the KB is empty
  (Requirement 5.2) without reaching into private state.

### 2. Fun-fact prompt builder (`prompt.py`)

A new function alongside the existing `build_messages`, sharing the same
grounding discipline but tuned for tone and brevity:

```python
def build_fun_fact_messages(context_snippets: list[str]) -> list[dict]:
    """System + user messages that ask for ONE short, fun, grounded fact."""
```

System prompt rules (anti-hallucination carried over from `/ask`):
1. Produce exactly one fun fact about BEON.tech.
2. Use ONLY the provided context; invent nothing (no facts, figures, names,
   URLs absent from context).
3. Keep it to at most two sentences, light and engaging in tone.
4. Do not restate the context verbatim — rephrase it as a fun fact.

The user message fences the numbered context snippets exactly as `/ask` does so
the model separates instruction from data.

### 3. Route handler + models (`main.py`)

```python
class Source(BaseModel):          # already exists; reused
    text: str
    score: float | None           # widened to allow None for random mode

class FunFactResponse(BaseModel):
    fact: str
    sources: list[Source]
    topic: str | None
    model: str
    timestamp: str

@app.get("/fun-fact", response_model=FunFactResponse)
async def fun_fact(topic: str | None = None) -> FunFactResponse: ...
```

Handler flow:
1. Normalize `topic`: strip; treat empty/whitespace as `None` (Requirement 2.3).
2. Guard empty KB: if `store.size == 0` → HTTP 503 with descriptive `error`
   (Requirement 5.2).
3. Retrieve context:
   - topic present → `store.retrieve(topic, k=2)`
   - topic absent  → `store.sample(k=1)`
4. Build messages via `build_fun_fact_messages` and call `llm.complete`.
5. Guard empty/unusable LLM output: if the returned text is empty after strip →
   HTTP 502 with descriptive `error` (Requirement 5.1).
6. Return `FunFactResponse` with `topic` echoed (or `null`), `sources`, the
   model id, and an ISO-8601 UTC `timestamp` via the existing `_now()` helper.

`GET` with no body naturally satisfies "no request body required" (Req 5.3).

### Note on the shared `Source` model

`score` is widened from `float` to `float | None`. The `/ask` path always
populates a real score, so its behavior is unchanged; only the random fun-fact
path emits `None`. This keeps one source model across both endpoints.

## Data Models

| Field       | Type               | Notes                                        |
|-------------|--------------------|----------------------------------------------|
| `fact`      | `str`              | The generated fun fact (≤ 2 sentences).      |
| `sources`   | `list[Source]`     | `{ text, score }`; `score` null when random. |
| `topic`     | `str \| null`      | Echo of the normalized topic, or null.       |
| `model`     | `str`              | vLLM model id from `LLMClient.model`.        |
| `timestamp` | `str` (ISO-8601)   | UTC, via existing `_now()`.                  |

## Error Handling

| Condition                         | Status | Body                                   |
|-----------------------------------|--------|----------------------------------------|
| Empty knowledge base              | 503    | `{ "error": "Knowledge base is empty." }` |
| LLM returns empty/unusable output | 502    | `{ "error": "Failed to generate a fun fact." }` |
| Normal success                    | 200    | `FunFactResponse`                      |

Errors return JSON via FastAPI's `HTTPException`/`JSONResponse` so the shape is
predictable. Topic edge cases (empty/whitespace) are handled by normalization,
not errors, per Requirement 2.3.

## Testing Strategy

Unit tests follow the established pattern: pytest + `pytest-asyncio`, httpx
`ASGITransport` against the in-process app — no running servers. The LLM and the
embedding model are the slow/external parts, so both are mocked:

- **Mock `LLMClient.complete`** to return a canned fun fact (and, in one test,
  an empty string to exercise the 502 guard).
- **Mock the `VectorStore`** (or inject a fake) so tests don't load MiniLM;
  assert the handler calls `retrieve` when a topic is present and `sample` when
  it is absent.

Cases:
1. `GET /fun-fact` (no topic) → 200, `topic` is null, `sample` used, `fact`
   non-empty, response shape valid.
2. `GET /fun-fact?topic=AI` → 200, `topic` echoed, `retrieve` used with the
   topic, `sources` populated with scores.
3. `GET /fun-fact?topic=%20` (whitespace) → treated as no topic (random path),
   `topic` null.
4. LLM returns empty → 502 with `error`.
5. Empty knowledge base → 503 with `error`.

An integration smoke check is added to the Bruno collection (`Fun Fact.bru`)
against the live service, consistent with the existing two-layer model.

## Correctness Properties

These invariants must hold for any valid implementation; the prompt, handler
guards, and tests exist to enforce them.

### Property 1: Grounding

Every returned `fact` is derived solely from the knowledge-base snippets passed
to the LLM. No fact introduces entities, figures, names, or URLs absent from the
provided context.

**Validates: Requirements 1.2, 4.3**

### Property 2: Source honesty

The `sources` array always reflects the snippets actually used to ground the
fact — real similarity scores in topic mode, `null` scores in random mode, and
never a fabricated score.

**Validates: Requirements 1.4, 3.1**

### Property 3: Topic normalization is total

Any `topic` input maps deterministically to exactly one mode: non-empty after
trimming selects retrieval mode; absent, empty, or whitespace-only selects random
mode. No input value produces an error.

**Validates: Requirements 2.1, 2.2, 2.3**

### Property 4: Response-shape stability

A 200 response always contains all of `fact`, `sources`, `topic`, `model`, and
`timestamp`, with `topic` null exactly when no usable topic was supplied. The
shape matches the `/ask` conventions.

**Validates: Requirements 3.1, 3.2, 3.3**

### Property 5: No silent empties

The service never returns a 200 with an empty `fact`. An empty or unusable LLM
result yields an error status instead.

**Validates: Requirements 5.1, 5.2**

### Property 6: Read-only and body-agnostic

The endpoint never mutates server state, and its behavior is independent of any
request body that may be sent.

**Validates: Requirements 5.3**
