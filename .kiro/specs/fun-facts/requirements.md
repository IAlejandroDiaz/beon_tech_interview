# Requirements — Fun Facts

## Introduction

The RAG service currently answers user questions grounded in the BEON.tech
knowledge base (`POST /ask`). This feature adds a playful, read-only companion
endpoint that surfaces a short, fun fact about BEON.tech generated by the LLM
and grounded strictly in the same knowledge-base context.

The goal is a lightweight, engaging way to showcase the knowledge base and the
retrieval + generation pipeline without the user having to ask a question. It
reuses the existing RAG building blocks (`knowledge_base`, `vector_store`,
`llm`, `prompt`) so the architecture stays cohesive and the anti-hallucination
guarantees carry over unchanged.

Scope is a single new HTTP endpoint returning JSON. There is no frontend in this
repo, so "display" means a structured JSON response consumable via curl/Bruno.

## Requirements

### Requirement 1 — Generate a context-grounded fun fact

**User Story:** As an API consumer, I want to request a fun fact about
BEON.tech, so that I get an engaging, true tidbit without having to phrase a
question.

#### Acceptance Criteria

1. WHEN a client sends `GET /fun-fact` THEN the service SHALL return HTTP 200
   with a JSON body containing a single generated fun fact.
2. WHEN a fun fact is generated THEN the service SHALL base it ONLY on the
   BEON.tech knowledge-base snippets and SHALL NOT introduce facts, figures,
   names, or URLs absent from that context.
3. WHEN a fun fact is generated THEN it SHALL be concise (at most two
   sentences) and phrased in a light, engaging tone.
4. WHEN the service generates the fun fact THEN the response SHALL include the
   source snippet(s) used to ground it, so the grounding is observable.

### Requirement 2 — Topic-focused fun facts (optional filter)

**User Story:** As an API consumer, I want to optionally steer the fun fact
toward a topic, so that I can get a fact about a specific aspect of BEON.tech.

#### Acceptance Criteria

1. WHEN a client sends `GET /fun-fact?topic=<text>` THEN the service SHALL use
   the topic to retrieve the most relevant knowledge-base snippet(s) and ground
   the fun fact in them.
2. WHEN no `topic` query parameter is provided THEN the service SHALL select a
   knowledge-base snippet at random to ground the fun fact.
3. WHEN the `topic` parameter is present but empty or whitespace-only THEN the
   service SHALL treat the request as if no topic were provided (random
   selection) rather than returning an error.

### Requirement 3 — Structured, consistent response shape

**User Story:** As an API consumer, I want a predictable JSON response, so that
I can integrate the endpoint reliably.

#### Acceptance Criteria

1. WHEN the endpoint responds successfully THEN the JSON SHALL contain:
   `fact` (string), `sources` (array of `{ text, score }`), `model` (string),
   and `timestamp` (ISO-8601 UTC string).
2. WHEN a `topic` was provided THEN the response SHALL echo it back in a
   `topic` field; WHEN no topic was provided THEN `topic` SHALL be `null`.
3. WHEN the response is serialized THEN the shape and field conventions SHALL
   mirror the existing `/ask` endpoint (same timestamp format, same
   `sources` structure) for consistency across the service.

### Requirement 4 — Reuse the existing RAG pipeline

**User Story:** As a maintainer, I want the feature built on the existing RAG
modules, so that the codebase stays cohesive and the retrieval/generation
behavior is consistent.

#### Acceptance Criteria

1. WHEN retrieval is needed THEN the service SHALL use the existing
   `VectorStore` rather than introducing a separate embedding or storage path.
2. WHEN the LLM is called THEN the service SHALL use the existing async
   `LLMClient` pointed at the local vLLM server, requiring no API key.
3. WHEN the prompt is constructed THEN the service SHALL use a dedicated
   fun-fact prompt that enforces the same grounding and anti-hallucination
   rules as the `/ask` prompt, adjusted only for the playful tone and brevity.

### Requirement 5 — Graceful behavior and error handling

**User Story:** As an API consumer, I want sensible behavior when things go
wrong, so that failures are clear rather than opaque.

#### Acceptance Criteria

1. WHEN the LLM returns an empty or unusable response THEN the service SHALL
   respond with an appropriate error status and a descriptive JSON `error`
   message rather than an empty `fact`.
2. WHEN the knowledge base is empty THEN the service SHALL respond with a
   descriptive error rather than attempting generation.
3. WHEN the endpoint handles a request THEN it SHALL NOT require a request body
   and SHALL ignore any body that is sent.
